## Problem Statement
Proof-of-work build for the Walnut Folks Group "AI Product Engineer (Freshers)" application. The JD asks for "AI workflows that screen, score or summarise campaign data." Post-Live Watch simulates the Confluencr account manager's post-launch workflow: once an Instagram campaign goes live, an AM has 20-100 creator posts to verify, track against promises, watch for sentiment problems, and triage into next actions — today done by hand in spreadsheets and WhatsApp. The system surfaces and triages 12 named post-live problems via transparent deterministic rules, with AI as an optional language/judgment layer on top (never the source of truth).

## What Makes This Cool
The rules-first/AI-on-top split is the whole point: every flag traces to a config value a reviewer can open and reason about, and the AI toggle proves the system still works correctly with AI fully off (keyword sentiment + template text). That's a much stronger "I understand how to build trustworthy AI systems" signal than a flashy LLM-wrapper demo — and it's exactly what the JD is screening for.

## Constraints
- Build-time target: 4-5 hours.
- Instagram only, web dashboard only. No live IG API — all data synthetic, labelled "SAMPLE DATA".
- Copy-and-send actions only — nothing auto-sends.
- Thresholds must live in one editable config file, not scattered in code.
- Must work end-to-end with AI fully off.

## Premises
1. **Local-run + self-hosted artifact, not a throwaway demo.** README + one-command startup is the baseline; it also runs live on the user's own Oracle Cloud VM (already hosting their n8n instance) via Docker, fronted by their existing reverse proxy. — agreed, revised from "optional hosting" to "actually deploy it."
2. **SQLite is the right database, not a shortcut.** Of the 12 detectors, only 4 get an AI *enhancement* layered on top of an already-fired rule (underperform explanation, Hinglish/sarcasm sentiment, paraphrase detection, boost suggestion) — 8 are pure deterministic checks. This is a rules engine with a thin language layer, not an AI-heavy app, at a tiny data volume (~20 creators, ≤100 posts, a few thousand rows total, one AM user, no concurrent writers). Postgres would add an operable service for zero correctness benefit. SQLite as a single file also makes the day-simulator trivial (advance a `current_day` pointer, re-query) and resets trivial (swap the file). Self-hosting on a real VM removes the "ephemeral filesystem" problem serverless would have created. — confirmed after explicit challenge.
3. **FastAPI owns all engine/data/logic. n8n is strictly the optional daily-report delivery trigger, nothing more.** Rejected using n8n for any part of the rules/scoring/AI pipeline: it has no native test story (the graded bar is "all 12 problems trigger on the right posts," which needs a real `pytest` suite), the brief's "thresholds live in a single editable config" requirement wants a YAML/JSON file read by Python not scattered node parameters, and the relational/transactional data model (campaigns → creators → posts → snapshots → comments → flags → decisions, 6 months of history) needs real joins/transactions n8n doesn't provide. n8n's one legitimate, brief-sanctioned role: a scheduled workflow on the user's existing n8n instance that calls `GET /api/brand-report` and delivers it (email/Slack/webhook) — exactly the brief's "optional" line, nothing in the critical path. — confirmed after explicit challenge.
4. **AI provider: OpenRouter, model card configurable via one env var.** Model card itself deferred — the single AI-calling function reads `OPENROUTER_MODEL` (or similar) so the model can be swapped later without touching code. Fits the "one LLM provider behind a single function with a template fallback" requirement exactly. — confirmed, model TBD.
5. **Frontend built externally by Claude Design, handed off as static HTML/CSS per screen; this build does the backend + the wiring.** Each screen (campaign overview, flag queue, creator profile, brand report, day-simulator control) gets a design brief (content inventory, data fields, interaction states) now; once static mockups come back, they get converted into Jinja2 templates with HTMX attributes added for the interactive bits (approve/dismiss, copy button, day-advance, AI toggle). — confirmed.
6. **"Done" = all 12 rules firing correctly on the right seeded posts + approval loop + profile + report + AI toggle, verified by build order, not left to chance.** Nothing in "out of scope" (auth, multi-tenant, real IG API, payments, mobile, auto-send) gets attempted even if time remains — any leftover time goes to frontend wiring polish, not scope expansion.

## Approaches Considered
### Approach A: Dashboard-First
Build FastAPI + Jinja2 + HTMX screen-by-screen in the brief's presentation order (overview → queue → approval → profile → report → simulator), backend and UI together as you go.
- Effort: M · Risk: Low-Med
- Pros: visible progress early; matches the brief's suggested stack with no surprises.
- Cons: under a hard time cap, rule-correctness work (the part actually graded: "all 12 problems trigger on the right posts") lands last, when time and attention are shortest.
- Rejected: too much risk that the hardest-to-verify part gets the least time.

### Approach B: Decoupled SPA
FastAPI as a pure JSON API; a React/Vite SPA (shadcn/ui) for the dashboard.
- Effort: L · Risk: Med
- Pros: more polished "production SaaS" look out of the box; demonstrates broader full-stack range.
- Cons: burns the scarcest resource (time) on frontend plumbing (API contracts, build pipeline, CORS) instead of the AI/rules logic that's the actual JD ask; highest risk of an unfinished feature under the 4-5h cap.
- Rejected: wrong place to spend the time budget for this specific ask. (Superseded further by premise 5 — frontend is externally designed, not hand-rolled either way.)

### Approach C: Engine-First (chosen)
Build and `pytest`-verify the rules/scoring engine, config-driven thresholds, reliability-score formula, and the thin AI layer (with template fallback) against seed data **first**, exposed via a `/debug` JSON endpoint, proving all 12 problems fire on the right posts before wiring any screen. Wrap the FastAPI+HTMX UI (built from Claude Design's static HTML/CSS handoff, per premise 5) around the verified engine last.
- Effort: M (same total build as A, reordered) · Risk: Low
- Pros: directly optimizes for the brief's hardest grading bar by front-loading it while attention is freshest; safe failure mode — if time runs short, there's still a demonstrably correct, tested engine (`pytest` output + `/debug` JSON) rather than a pretty dashboard sitting on an unverified one.
- Cons: no visible UI to show until later in the build.

## Recommended Approach
**Approach C (Engine-First)**, with the backend/infra choices from the Premises section: FastAPI owns the rules engine, data model, and the single OpenRouter-backed AI function (template fallback when AI is off); SQLite as the persistent store; n8n limited to the optional daily brand-report delivery trigger on the user's existing instance; the whole stack self-hosted via Docker on the user's Oracle Cloud VM; frontend screens designed externally by Claude Design as static HTML/CSS and wired into Jinja2+HTMX templates last.

## Decisions log
- **Campaign brief is a default, not a law (2026-10-19).** Raised via `/office-hours`: the original
  schema treated `campaigns.required_disclosure/required_tag/required_hashtag/requires_link_sticker`
  as universal across every creator, and every consumer picked exactly one deliverable per creator
  via an unordered `.fetchone()`. Real deals negotiate terms away, pay differently (barter,
  affiliate), and bundle multiple deliverables. Fixed by making `deliverables` carry nullable
  overrides resolved in one place (`app/rules/contract.py`), with the resolution surfaced as
  `contract_notes` rather than a rule silently not firing, and by fetching every deliverable a
  creator has instead of an arbitrary one. This also fixed three live bugs the old model was
  hiding: a dead `requires_link_sticker` column, rule 3 ignoring the `required_disclosure` field
  it claimed to check, and a hardcoded reach-floor check that would misflag barter creators who
  never promised a reach number. See `README.md`'s "The campaign brief is a default, not a law".

## Success Criteria
- Seed loads cleanly (20 creators, 1 live 7-day campaign with ~20 posts mixing ~8 healthy / ~12 problem posts, 6 months of history per creator).
- All 12 named problems trigger on exactly the right seeded posts, verified by a passing `pytest` suite and visible in the `/debug` JSON endpoint — independent of whether the UI is finished.
- Approval flow works end-to-end (Approve/Edit/Dismiss → copy-paste message generated → decision logged with timestamp).
- Creator profile and brand daily report render correctly from real computed data (not hardcoded).
- AI on/off toggle demonstrably changes behavior (LLM-generated language vs. keyword/template fallback) without breaking any flow.
- README explains how to run it locally and how it's deployed on the Oracle VM.

## Distribution Plan
Self-hosted web service: Docker container on the user's existing Oracle Cloud Linux VM, alongside their n8n instance, behind whatever reverse proxy that instance already uses. No separate CI/CD pipeline needed for a single-VM deploy at this scope — a `docker compose up -d --build` on the box after a `git pull` is sufficient; document the exact steps in the README.
